Event-Driven Strategy: UNDER After 3PT Make

NBA live player-points props  ·  Phase 1  ·  20-player bucket  ·  1 bookmaker
Written 2026-05-22

Event-driven UNDER only Live betting Phase 1: Notebook backtest
One-line thesis: When a player hits a three-pointer in the final ~60 seconds of real play, bookmakers may briefly inflate the live line to account for the new points — creating a window where the UNDER is mis-priced. We only trade this if our Monte Carlo model confirms an edge vs the posted line and the live points counter has actually moved (verifying we have the correct, updated line).
Phase 1 is a notebook backtest, not live deployment. All required data already exists: signals parquets in S3 contain save_timestamp_utc, player_name, current_points, game_id, and bet_side. The ESPN Summary API returns the full play history for any completed game. The backtest retroactively applies the 3PT trigger filter to existing signals — no new API calls, no S3 writes, no live loop changes needed yet.

1. The Edge Hypothesis

Why UNDERs specifically?

A 3-pointer adds 3 points instantly. Bookmakers re-price the live line upward to reflect the new total — but if they over-correct (or correct slowly), the remaining-points requirement becomes too high, making UNDER the value side.

This is the opposite of a "hot hand" bet. We're fading the line adjustment, not the player.

Why "last 60s"?

The 60-second window aligns exactly with our polling cadence. Analysis of save_timestamp_utc across the signals data confirms the generator runs at a median 59.8 s interval (mode: 60 s, n=133 intervals from 20260519). A 3PT make within the last 60s is therefore one that happened in the gap since the previous MC scan — it is structurally guaranteed to be new information not yet incorporated into prior signals.

Wider windows (e.g. 90 s) would pull in makes the model already priced in the previous iteration, diluting the edge. Narrower windows risk missing makes that occurred just before a poll fired.

Key guardrail: The current_points field in the live signal must have increased relative to the most recent prior snapshot for the same player. This confirms the ESPN boxscore has already registered the 3PT make — so we know the live line we're trading against is the post-make price, not a stale pre-make line.

2. Execution Flow

1
Fetch live PBP from ESPN Summary API GET /apis/site/v2/sports/basketball/nba/summary?event={game_id}  — already done in 10_live_betting_signal_generator.py:fetch_and_validate_pbp(). Returns data['plays'], each play has text, wallclock, period.number, clock.displayValue.
G1
Gate: 3PT make in last 60 seconds (wall clock) Filter plays where text matches "makes 3-pt" (case-insensitive) AND wallclock is within 60 s of current UTC time. Player name extracted from play text (first two words, e.g. "Nikola Jokic"). If no qualifying play: skip player, no MC needed.
G2
Gate: Player is in the 20-player bucket Hard-coded allowlist of 20 high-volume 3PT shooters (see §5). No API cost — PBP and odds data are already in memory from the main 60 s loop. This gate exists only to limit Phase 1 exposure while the hypothesis is being validated, and to focus on players where the 3PT→line-adjustment dynamic is most pronounced.
G3
Gate: Live line is fresh (<60 s) from non-stale bookmaker Re-uses existing staleness check from 10_live_betting_signal_generator.py. Must come from the single designated bookmaker (Phase 1: one fresh bookmaker, determined by lowest Brier score in 12_brier_by_bookmaker.py output). Bovada and any bookmaker with stale=True are excluded.
G4
Gate: Live points jumped vs prior snapshot Compare current_points for this player against the last saved snapshot (in-memory dict, keyed by game_id + player_name). Required increase: current_points_now - current_points_prev >= 2 (a 3PT is +3, but at minimum +2 rules out a spurious non-scoring update). This confirms ESPN boxscore has propagated the make and the live line reflects the new total.
2
Run Monte Carlo simulation for UNDER only Re-uses monte_carlo_simulate_bet() from monte_carlo_utils.py, fixing bet_side="UNDER". Inputs: current_points, live_line, game_minute, player profile from minute_by_minute.parquet. 5,000 simulations (same as main generator default).
G5
Gate: Edge vs posted line exceeds threshold model_prob_under > implied_prob_under_no_vig + MIN_EDGE. Market implied probability from remove_vig() using posted over/under odds. Backtest starting point: MIN_EDGE = 0.10 (10 pp, same as main generator). The notebook will sweep multiple thresholds — 5 / 10 / 15 / 20 pp — to find where signal count vs hit-rate trade-off is optimal. Higher thresholds = fewer but cleaner signals.
3
Tag signal in notebook (no S3 write) In the backtest notebook, flag matching rows with trigger_event="3pt_make" and trigger_play_text (raw play description). Compare performance of tagged vs untagged signals in-notebook. No parquet writes or S3 uploads needed for Phase 1 — all data lives in memory. If the backtest shows edge, the tagging logic is promoted into the live loop.

4. Implementation Plan

No new MC runs needed. The main generator already runs Monte Carlo for every active player every 60 s. This strategy is a post-filter layered inside the existing loop: after MC results are produced, check if any UNDER signal comes from a player who just hit a 3PT. If yes → tag it as a triggered signal and write to the separate output path. No additional Odds API calls, no additional ESPN calls, no additional simulations.

6. Guardrails Summary

GuardrailParameterRationale
3PT recency window window_seconds = 60 Matches the polling cadence exactly (empirically confirmed: median 59.8 s, mode 60 s across signals data). A make within this window is one that occurred since the last MC scan — structurally new information. Older makes were already seen in a prior iteration.
Points jump check min_increase = 3.0 A 3PT make is exactly +3 pts — requiring a ≥3 pt jump verifies both that ESPN has registered the score and that the live line we're trading against is the post-make price. A threshold of 2 would pass spurious updates (e.g. a non-scoring play that updates the boxscore).
Player bucket 20 players, hard-coded allowlist Limits Phase 1 scope and Odds API usage. Players without pregame lines are skipped anyway by existing Gate 4.
Single bookmaker 1 bookmaker allowlist Avoids taking signals on bookmakers with historically stale lines (measured by Brier score in script 12).
Odds freshness MAX_ODDS_AGE_SECONDS = 60 Inherited from main generator. If the bookmaker hasn't updated in >60 s, the line is pre-make and we skip.
UNDER only Hard-coded bet_side = "UNDER" The hypothesis is specifically about post-make over-correction. OVERs after a 3PT are a different (untested) thesis.
Min edge threshold MIN_EDGE = 0.10 (backtest start) Starting value for the notebook sweep. Backtest will compare 5 / 10 / 15 / 20 pp to find the optimal signal-count vs hit-rate balance. Higher threshold = fewer signals, cleaner edge required.
Model prob cap MODEL_PROB_CAP = 0.85 Inherited from main generator. Prevents overconfident signals on already-decided lines.

7. Evaluation Plan

All evaluation tooling is reusable unchanged. The new S3 path player_points_3pt_trigger/ is the only difference — pass it as an env or path arg.

Primary metrics

  • Brier score — is the model calibrated on this specific trigger context? Expect slightly higher (harder) than baseline since the market just re-priced.
  • ROI — flat $100 per signal, same as existing evaluation.
  • Hit rate on UNDER — null hypothesis: ~50% (coin flip). We need >52.4% at -110 to break even.
  • Signals per game — if <1 per game night on average, the strategy is too sparse to be useful.

Secondary cuts

  • By quarter (Q1–Q4): is the edge concentrated in early quarters (line still adjusting) or late (line settled)?
  • By game minute at trigger: does the edge decay as game approaches end (fewer points remaining = tighter distribution)?
  • By points gap at trigger: live_line - current_points — large remaining gap = more MC uncertainty; small gap = UNDER more probable already.
  • By player: some players may have cleaner signals than others (test for player-level Brier).

Sample size target before go/no-go

Minimum 50 evaluated signals across at least 10 game days before drawing conclusions. With 20 players and 1 bookmaker, expect 5–15 signals per game night (depending on 3PT rates and gate passage). Aim to hit this in ~7 game nights.

Add a --3pt-trigger flag that enables the post-filter and writes tagged signals to the separate S3 path. The --bookmaker flag already exists (or can be added) to restrict Phase 1 output to a single bookmaker.
