⚠ CORRECTION: Steps 3a/3b/3c Used Wrong Modeling Approach

What was done (wrong)

Steps 3a–3c trained binary classifiers predicting P(hit_over) and P(hit_under) directly as the model target. This is incorrect for two reasons:

  1. Line conflation: hit_over/hit_under is a function of both the game outcome AND the line. A game scoring 9 runs hits the over at line 8.5 but not at line 9.5. By training on hit_over directly, the model's features are explaining whether the BET hit — which is partly market line placement — rather than whether the game scored runs.
  2. Cannot generalize across lines: A model predicting P(hit_over at line 9.5) has no way to generate a prediction for a game with line 8.5. You'd need a separate model per line. The total bases pipeline solves this correctly by predicting y_hat (the raw stat) once, then calibrating to any line.

The AUC of 0.52 we observed was essentially the model detecting the line value itself (higher line → more likely to go over relative to its prior calibration). Not real signal.

Correct approach

  1. Step 3: Train a regression model predicting total_runs (continuous). Target is the actual score, not the bet outcome. Sweep individual features by r². Then train XGBoost regressor with constrained feature set (only features with positive individual r²).
  2. Step 4: Method C calibration — using OOF y_hat from the regression, fit a per-line logistic regression: P(hit_over | y_hat) for each distinct line value. This maps the regression output to a probability at the specific line being priced.
  3. Step 5: Backtest — edge_under = (1 - P(over | y_hat, line)) - raw_prob_under. Grid search over edge thresholds.
  4. Step 6: Temporal OOS (train 2024 → test 2025, train 2024+2025 → test 2026).

What we already know going in

  • Individual feature r² vs total_runs is very low: best is consensus_line at 0.022, park_factor at 0.004, combined_ra/rs at <0.003. The market is hard to beat.
  • XGBoost with all 56 features got r² = -0.012 (worse than mean) — heavy overfitting. We must use only features with positive individual r² and constrain the model.
  • Expected OOF r² for correct model: ~0.025–0.030 (small but positive). The calibration step can still produce meaningful edge even at low r².
  • The 9.5 under calibration edge (+3.9pp vs novig, +9.5% OOS ROI in 2025) is real and not model-dependent — it comes from the line bucket itself. The question is whether the regression y_hat adds signal ON TOP of that calibration edge by finding better vs worse 9.5 games.

Steps 3a/3b/3c below are SUPERSEDED — do not use for production

The grid search results from Steps 4+5 and OOS results from Step 6 are also invalidated because they were built on the wrong model outputs.

⚠ CORRECTION: Steps 3a/3b/3c Used Wrong Modeling Approach

What was done (wrong)

Steps 3a–3c trained binary classifiers predicting P(hit_over) and P(hit_under) directly as the model target. This is incorrect for two reasons:

  1. Line conflation: hit_over/hit_under is a function of both the game outcome AND the line. A game scoring 9 runs hits the over at line 8.5 but not at line 9.5. By training on hit_over directly, the model's features are explaining whether the BET hit — which is partly market line placement — rather than whether the game scored runs.
  2. Cannot generalize across lines: A model predicting P(hit_over at line 9.5) has no way to generate a prediction for a game with line 8.5. You'd need a separate model per line. The total bases pipeline solves this correctly by predicting y_hat (the raw stat) once, then calibrating to any line.

The AUC of 0.52 we observed was essentially the model detecting the line value itself (higher line → more likely to go over relative to its prior calibration). Not real signal.

Correct approach

  1. Step 3: Train a regression model predicting total_runs (continuous). Target is the actual score, not the bet outcome. Sweep individual features by r². Then train XGBoost regressor with constrained feature set (only features with positive individual r²).
  2. Step 4: Method C calibration — using OOF y_hat from the regression, fit a per-line logistic regression: P(hit_over | y_hat) for each distinct line value. This maps the regression output to a probability at the specific line being priced.
  3. Step 5: Backtest — edge_under = (1 - P(over | y_hat, line)) - raw_prob_under. Grid search over edge thresholds.
  4. Step 6: Temporal OOS (train 2024 → test 2025, train 2024+2025 → test 2026).

What we already know going in

  • Individual feature r² vs total_runs is very low: best is consensus_line at 0.022, park_factor at 0.004, combined_ra/rs at <0.003. The market is hard to beat.
  • XGBoost with all 56 features got r² = -0.012 (worse than mean) — heavy overfitting. We must use only features with positive individual r² and constrain the model.
  • Expected OOF r² for correct model: ~0.025–0.030 (small but positive). The calibration step can still produce meaningful edge even at low r².
  • The 9.5 under calibration edge (+3.9pp vs novig, +9.5% OOS ROI in 2025) is real and not model-dependent — it comes from the line bucket itself. The question is whether the regression y_hat adds signal ON TOP of that calibration edge by finding better vs worse 9.5 games.

  1. 10:00am ET — pipeline mode: Load spine from S3 (4,400+ games, all pre-target-date). Build team rolling-stat lookup (most recent game per team). Train Ridge(α=50) on all historical game-level features. Fit Method C per-line calibration (logistic y_hat→P(over|line)) on training games. Fetch live game totals from Odds API. Build feature vector for each game (consensus_line + park_factor + team rolling stats). Score all lines. Qualify: line=9.5, edge>0. Send HTML email. Write picks.csv to S3.
  2. 11:00am ET — settle mode: Load yesterday's qualifying_bets.csv from S3. Fetch final scores from MLB Stats API. Settle (under 9.5 wins if total_runs < 9.5). Append to cumulative settled parquet. Send settle email.

Key Design Decisions

  • Re-train daily (not pre-trained artifact): Ridge is fast (<1s on 4,400 games). Model benefits from including most recent games. Calibration also benefits from fresh fit. No S3 model artifact to manage.
  • Team feature lookup: From spine, build per-team rolling stats by finding each team's most recent game (as home or away). Rename to generic rs_/ra_ prefix, then attach to today's home/away matchups.
  • Edge = p_model_under - raw_prob_under (vig-inclusive per skill spec). Benchmark: bet ALL 9.5 unders = +8.45% OOS ROI. Model edge>0 filter = +13.65% OOS ROI (n=383).
  • EventBridge rules DISABLED at deploy time. Enable manually after confirming pipeline output is correct on a live day.

Key Findings

  1. Plus-odds 9.5 unders are the sharpest signal (model: n=55, hit=72.7%, ROI=+46.85%, net/MDD=6.44x). When a book prices the 9.5 under at plus-odds, it means the book thinks the game is likely to go OVER — but the under still wins 72.7% of the time OOS. Only 5.7% of 9.5 under rows are plus-odds (≈27 bets/year) so n is thin.
  2. Rolling features (RA/RS, park_factor) add nothing. Consensus_line alone as the sole predictor outperforms the 12-feature Ridge at almost every threshold. The market's own priced total already contains the relevant signal.
  3. Consensus_line + minus_odds + edge≥0.07 is the strongest large-n config: n=181, hit=72.9%, ROI=+41.83%, MDD=-11u, net/MDD=6.88x.
  4. Model shrinkage=0.25 (75/25 model/market blend) materially improves the full model: net/MDD goes from 1.07x to 3.97x by filtering out low-confidence model calls.
  5. The original "bet all 9.5 unders" conclusion was wrong — it is NOT the best config. It is the highest-n config but has the worst risk-adjusted return (net/MDD=2.54x from step6b vs 6.88x for the best configs here).
